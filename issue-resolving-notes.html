2026-05-25 Clerk Data Isolation Fix

The known auth/data issue is now treated as a reviewable branch change: server routes derive the active user from Clerk instead of accepting a browser-supplied userId.

Design Decisions

  • Use auth() from @clerk/nextjs/server in route handlers and pass that Clerk user ID into QA, summarization, selection summaries, skills lookup, and chat history persistence.
  • Replace the chat history route's process-local Map with Postgres-backed chat_sessions and chat_messages tables keyed by user_id, paper_id, and session_id.
  • Keep Clerk's user ID as the application user key instead of adding a separate users table, matching the existing persona schema that already stores opaque text user IDs.
  • Keep /api/skills/[userId] as a disabled legacy route that returns 410; the supported route is now /api/skills for the authenticated user.
  • Validate and sanitize chat citation metadata before writing assistant messages to Postgres. The accepted citation fields cover both existing chat shapes: id/title/url/page and chunkId/quote/page.

Deviations

  • The previous demo/default user fallback was removed from personalized routes. Signed-out requests now receive 401 for routes that create or read personalized data.
  • Existing in-memory chat history is not migrated because it was only process-local runtime state and was not durable across Vercel function instances.
  • Invalid chat message payloads now return 400 instead of falling through to a generic server error.

Tradeoffs

  • I chose authenticated-only personalized endpoints over anonymous browser IDs. Anonymous IDs would preserve guest usage but still require a separate trust and merge model before it could safely become account data.
  • I added database chat persistence now rather than only scoping the existing in-memory map. Serverless memory is not durable, so a scoped map would still make "stored chats" misleading on Vercel.
  • I preserved the old messageCount response meaning as the total messages in the session, even though the current client does not read that field.

Open Questions

  • Confirm whether you want any signed-out read-only or no-persistence QA mode, or whether all LLM-backed personalized actions should stay sign-in only.
  • Confirm when to remove the disabled legacy /api/skills/[userId] route entirely after clients have moved to /api/skills.
